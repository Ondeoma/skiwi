# skiwi の設計

## 1. 要件サマリ

| 区分 | 内容 |
|---|---|
| 認証 | OIDC（任意のIdP）。ユーザー・グループ同期、APIトークン |
| エディタ | ブロックエディタ（スラッシュコマンド）、データベース |
| 同時編集 | CRDT。想定規模の目安は、1ページの同時接続が約20人、ユーザーが100名程度 |
| 日本語 | UI、IME入力、全文検索、フォントを対応（縦書きとルビは対象外） |
| 構造 | ワークスペース、ツリー型ページ階層 |
| 権限 | ページ単位の閲覧・編集の2権限。IdPのグループと連携 |
| 機能 | 版履歴、全文検索、メール通知、監査ログ、REST API |
| 基盤 | 3ノード冗長。Patroni（PostgreSQL）と S3 互換ストレージ（添付ファイル）。Redis等は使わない |
| 実装 | バックエンドはScala（Cats Effect、http4s、doobie、sbt）。フロントは Scala.js + Scalactive（兄弟のサービスと同じ作り）。エディタとCRDTはTiptap + Yjs（TypeScript） |

## 2. 全体アーキテクチャ

```
        Browser (Tiptap + Yjs)
           │ HTTPS / WebSocket
   ┌───────▼────────┐   VIP(keepalived) + HAProxy
   │ node1 node2 node3│  ← 各ノードで同一構成
   │  skiwi-app (Scala)│  http4s: REST / WS / SCIM
   │  Patroni+PG      │  PostgreSQL + PGroonga
   │  etcd            │  Patroniのコンセンサス
   │  S3互換ストレージ  │  添付ファイル
   └──────────────────┘
        ▲ OIDC / SCIM
     IdP（OIDC / SCIM）
```

- アプリはステートレスに近い構成で、3ノードすべてで動かします。
- 状態はPostgreSQL（Patroni）と S3 互換ストレージに集約します。
- ノード間通信はPostgreSQLの `LISTEN/NOTIFY` を使い、Redisなどは追加しません。

## 3. 同時編集の設計（最重要）

**方針：同時編集の経路では、サーバーはYjsを解釈しない「リレー兼永続化層」にする。** JVM向けの成熟したYjs実装がないため、この方針でScalaだけでサーバーを完結させます。

### 3.1 プロトコル
- クライアントは `y-websocket` 互換のプロトコル（sync step1/step2/update と awareness）を使います。
- サーバーは外側のフレーム（messageType、varint）だけをパースし、Yjsの中身はバイト列のまま扱います。
- 認可は次のように行います。
  - 閲覧のみのユーザーのupdateメッセージは破棄します。
  - awarenessは中継します。

### 3.2 永続化
- `page_updates` に、受信したupdateを追記します（`seq bigserial, page_id, data`）。
- 接続時は、スナップショット(step2)、それ以降のupdate、同期完了マーカー（空のstep2）の順に送ります。
  **サーバーはstate vectorを持たないため、クライアントのstep1は無視し、毎回全状態を送ります。**
- **コンパクション**：サーバーはマージできないため、接続中の編集可能なクライアント1人にスナップショットを依頼します。
  - 独自メッセージ：`[100][token]`（要求）／`[101][token][update][json][text]`（応答）。
  - 要求は「更新が200件たまった」または「最後の更新から5秒経過」で発行します。応答の待機は30秒です。
  - 応答のupdate・ProseMirror JSON・平文テキストを `page_snapshot(kind='compact')` に保存し、要求時点の最大seq以下のupdateを削除します。
  - **安全性の根拠**：「永続化→配信」を部屋のロック内で行うため、要求の時点までのupdateは、要求を受け取るクライアントが必ず適用済みです。
  - 応答は、要求したトークンと宛先クライアントが一致し、編集権限がある場合のみ受理します。
- 平文テキストは検索インデックスと版履歴に使います。編集権限のあるクライアントが送る値をそのまま使うため、悪意のある編集者は本文と食い違う平文を登録できます（既知の制約）。
- **クライアント側の再送**：切断中や接続前のローカル編集は、同期完了後に全状態をupdateとして再送します（CRDTなので冪等）。
- `y-websocket` の BroadcastChannel（同一ブラウザのタブ間の直接同期）は無効にし、サーバー（認可と永続化）を唯一の経路にします。

### 3.2.1 既知の制約
- ルームの購読キューは有界（1024）で、極端に遅いクライアントがいると配信が詰まる可能性があります。
- 再接続のたびにクライアント全状態の再送が発生し得ます（コンパクションで吸収）。
- 圧縮の担い手がいない（閲覧者のみ接続など）場合、ログは次回の編集者の接続まで残ります。

### 3.2.2 接続中の権限再検証
- 接続時と権限変更時に、サーバーが独自メッセージ `[102][role]`（`edit` / `view` / `none`）でクライアントへ権限を通知します。
- ACL変更、ページの移動・削除、SCIMによるユーザー無効化・グループ変更の直後と、60秒ごとの定期処理で、接続中の全クライアントについて
  セッション（グループ所属を含む）を引き直して権限を再計算します。
  - 降格（編集→閲覧）: 以後のupdateを破棄し、クライアントは編集不可に切り替わります。
  - 取り消し: `none` を送って接続を閉じ、クライアントは再接続しません。
- 3ノード構成では `NOTIFY` で他ノードへ伝播させます（定期処理で最大60秒以内には追従）。

### 3.3 3ノード構成
- **担当ノード（親和性）**：`pageId` から **rendezvous hashing** で担当ノードを決めます。担当でないノードが受けたWebSocketは、
  担当ノードへ内部転送します（`X-Skiwi-Forwarded` ＋ 共通の `CLUSTER_SECRET`）。ロードバランサーは単純なラウンドロビンで済みます。
  同じページの編集者は同じノードに集まるため、配信・カーソル表示・圧縮がノード内で完結します。
- **生存確認**：各ノードが5秒ごとに `cluster_node` へハートビートを書き、15秒以内に書いたノードを生存とみなします（etcd等は使わない）。
  正常停止時は登録を即座に消します。生存ノード集合が変わると、担当でなくなったページの接続を閉じ、クライアントは担当ノードへ繋ぎ直します。
  担当ノードに転送できない場合（停止直後など）は、受けたノードで処理します。
- **正しさは親和性に依存しない**：同じページが一時的に複数ノードで開かれても（切替中・ネットワーク分断）、内容は失われません。
  - すべてのupdateはDBに保存したうえで `NOTIFY skiwi_update` で他ノードへ通知し、そのページを開いているノードは配信します。
  - **圧縮は「圧縮したクライアントに届けたと分かっているもの」だけを消します**（updateのseqとスナップショットのIDを接続ごとに記録）。
    （要求時点の最大seq以下を一律に消すと、ノードをまたいだときに未配信のupdateを消し得るため）
    消し残しは状態断片（`kind='part'`）として残り、接続時にまとめて送ります（Yjsは冪等）。断片が増えたら接続時に圧縮します。
  - `LISTEN` 接続が切れた場合（DBフェイルオーバー等）は再接続後に、開いている全ページの内容を流し直します。
- 権限変更の再検証も `NOTIFY skiwi_access` で全ノードへ伝えます（加えて60秒ごとの定期再検証）。
- 障害時の挙動（`frontend/test/ha-e2e.mjs`、Docker上の3ノード）:
  | 障害 | 結果 |
  |---|---|
  | 担当アプリノードの停止（正常停止） | 即座に別ノードへ切替。停止中の編集を含め全件保存・全員一致 |
  | 担当アプリノードの強制終了 | 約10〜15秒で切替（ハートビート切れ）。データ損失なし |
  | 停止ノードの復帰 | 自動で再参加し、担当ページの接続が戻る |
  | DBプライマリの停止・強制終了 | Patroniが約15〜20秒で昇格。その間の本文の編集はクライアント再接続・再送で回復し、失われない（試験環境での確認。非同期レプリケーションのため、本文以外の直前の数件の書き込みは失われ得る） |
  | 停止したDBノードの復帰 | レプリカとして自動で再参加（pg_rewindが使えない場合はデータを取り直す） |
  | 上記の強制終了を連続 | 2回連続でも成功（フェイルオーバー後の全文検索・ページ作成も確認） |
- 構成上の注意: PGroonga索引をレプリカに複製するため WALリソースマネージャを有効にします。強制終了した旧プライマリの再参加と、
  分岐したノードの昇格によるデータ消失を防ぐため `remove_data_directory_on_rewind_failure` と `check_timeline` を使います。
  アプリノードは待ち受けを始めてから生存登録し、担当ノードの応答を確かめながら定期的に再配置します。

## 4. データモデル（PostgreSQL）

- `workspace(id, name, ...)`
- `page(id, workspace_id, parent_id, position, title, icon, created_by, deleted_at)`
  - 並び順は fractional index を使い、ツリー取得には `ltree` または再帰CTEを使います。
- `page_acl(page_id, principal_type[user|group], principal_id, role[view|edit])`
  - 上位ページから継承し、下位で上書きできます。
  - ワークスペース既定の権限も持ちます。
- `page_updates(page_id, seq, update bytea)`
- `page_snapshot(page_id, version, ydoc bytea, content jsonb, plain_text, created_by, created_at)`
  - 版履歴は、一定間隔と明示操作でスナップショットを残します。
- `app_user`（`sub`・`disabled` など）, `user_group`, `group_member`：IdPから同期します。
- `api_key(id, user_id, name, key_hash, scopes, expires_at, last_used_at, revoked_at)`：ハッシュのみ保存します（`scopes` は `{read}` か `{read,write}`）。
- `attachment(id, page_id, s3_key, size, content_type, sha256)`
- `audit_log(id, at, actor, action, target, detail jsonb)`：追記専用です。
- `page_watch(page_id, user_id)`：更新通知の購読。
- `mail_outbox(user_id, kind, page_id, dedupe_key, detail, not_before, attempts, sent_at, skipped)`：メール通知用のアウトボックスです。ワーカーがSMTPへ送信します。

## 5. 認証・認可

- **ログイン**：OIDC（Authorization Code + PKCE）。ID tokenの `groups` クレームも取り込みます。
- **同期**：IdPから **SCIM 2.0** でユーザーとグループをプッシュしてもらいます。
  - skiwi 側にSCIMエンドポイント（`/scim/v2/Users`, `/Groups`）を実装します。
  - ログイン時のクレームは補助とし、SCIMを正とします。
- **APIトークン**：ユーザーが発行します。`Bearer` で認証し、権限はユーザーに準じます。操作は監査ログに記録します。
- **認可**：ページ単位に、ユーザーとそのグループのACLをマージして判定します。WSの各メッセージでも検証します。
  - 親ページの削除・完全削除は、いっしょに消える子孫をすべて編集できる人だけが行えます。元の親が削除済みのページをゴミ箱から戻す（直下に移る）には、ワークスペースの直下に作れる権限が要ります。
- **全体の防御**（`Security.scala`）：
  - CSRF：Cookie で認証する更新系のリクエストは、`Origin`（なければ `Sec-Fetch-Site`）が同じオリジンのものだけを受け付けます。ログインの `state` はブラウザの Cookie にも結び付けます。
  - 本文の大きさ：`/api` は16MB、取り込みは64MB、それ以外（`/auth`・`/oauth`・`/scim`）は1MBまで。添付ファイルは各ルートの上限（100MB）。JSON の入れ子は256段まで。
  - ヘッダ：`X-Content-Type-Options: nosniff`・`Referrer-Policy: strict-origin-when-cross-origin`・`X-Frame-Options: SAMEORIGIN`、https なら HSTS。
  - サーバーから外への接続（リンクのカード・Webhook）は、社内・特殊用途のアドレスへは行いません（`NetGuard`。`UNFURL_ALLOW_PRIVATE`・`WEBHOOK_ALLOW_PRIVATE` で許可）。
  - 本文の属性に入った URL（埋め込み・リンクカード・ファイル・図）は、画面に出す直前に検査します（Scala.js の `skiwi.web.editor.SafeUrl`）。同時編集では属性を好きな値にできるためです。

## 6. 検索（日本語）

- PGroonga の全文検索インデックスを `page.title` と `page_snapshot.plain_text` に作成します。
  - 既定のトークナイザ（バイグラム）と NormalizerAuto により、日本語の部分一致、全角/半角、大文字/小文字を吸収します。
  - 入力は空白で分割し、各語をフレーズとしてエスケープしてAND検索します（クエリ構文の注入を防ぐ）。
  - スニペットは `pgroonga_snippet_html`（HTMLエスケープ済み、キーワードのみ装飾）を使います。
- 本文の検索対象は圧縮スナップショットの平文です。編集後、圧縮（最後の更新から約5秒）までは検索に反映されません。
- Patroniの全ノードにPGroongaを導入します。開発環境は `groonga/pgroonga` イメージを使います。
- 検索結果は、取得後にワークスペース単位で権限を解決し、閲覧できるページだけに絞り込みます。

## 7. 添付ファイル

- S3 互換ストレージに保存し、Scalaからは AWS SDK v2（同期クライアント、パス形式）で扱います。開発環境は [ScalaS3](https://github.com/Ondeoma/ScalaS3) です。
- アップロードはアプリ経由（multipart、要Edit）。一時ファイルに書きながらサイズ上限（既定100MB）とSHA-256を計算し、S3キー `pages/{pageId}/{attachmentId}` に保存します。
- ダウンロードもアプリ経由で、添付元ページの閲覧権限を確認します。
- XSS対策：画像・PDF・動画・音声・プレーンテキストのみインライン表示し、それ以外（HTML、SVGなど）は `application/octet-stream` で強制ダウンロードします。全レスポンスに `nosniff`、PDF以外に `CSP: sandbox` を付けます。
- 既知の制約：本文から削除された添付の実体は残ります（ガベージコレクションは未実装）。画像を別ページへコピーした場合、元ページの閲覧権限がないと表示できません。

## 8. 版履歴・通知・監査・API

- **版履歴**：`page_snapshot(kind='version')` に、本文JSON・平文・Yjs状態・作者（前回の版以降に編集した人）・任意ラベルを保存します。
  - 自動: 圧縮のたびに、直近の版から10分以上経ち、かつ本文が変わっていれば版を作ります。
  - 手動: 「現在の版を保存」（ラベル付き）。
  - 復元: サーバーは版の本文を返し、クライアントがエディタの内容を置き換えます（通常の編集としてYjs経由で全員に同期）。
    その直前に現在の状態を「復元前の状態」として版に残します。サーバーはYjsを解釈しないため、この方式にしています。
  - 保持期間は無期限です。差分表示（現在との差分・前の版との差分）はクライアントで計算します。
- **メール通知**：`mail_outbox` に積み、ワーカー（`modules/notify`、30秒ごと）がSMTPで送信します。
  - イベント: **ページ更新**（ウォッチ中の人へ。編集者本人を除く）、**共有**（新たに権限を付与・格上げされた人へ。グループは所属者に展開）。
  - 更新通知はページ×受信者ごとに1通へまとめ、編集が5分止まったら送信、最長でも30分で送信します（`dedupe_key` による集約）。
  - 本文は送信時に組み立て、その時点で閲覧できない宛先には送りません（権限変更・削除後の漏洩防止）。メールアドレスのない人・無効ユーザーはスキップ。
  - 失敗時は指数バックオフで最大10回再試行。複数ノードでも `FOR UPDATE SKIP LOCKED` で重複送信しません。
  - 作成者は作成したページを自動でウォッチします。
- **監査ログ**：`audit_log` は追記専用（UPDATE/DELETEをトリガーで拒否）。経路（画面/API/SCIM）、操作者、対象、詳細(JSON)を記録します。
  - 対象: ログイン・ログアウト・ログイン拒否、ワークスペース作成・共有設定、ページの作成・名前変更・移動・削除・共有設定、
    版の保存・復元、添付のアップロード、APIトークンの発行・失効、SCIMによるユーザー・グループ変更。閲覧は記録しません。
  - 管理者は画面（監査ログ）とAPIで参照できます。記録の失敗は本処理を失敗させず、ログに出力します。
- **APIトークン**：`skiwi_` で始まるランダム値。ハッシュのみ保存。スコープ `read`（GETのみ）/ `write`（ユーザーの権限どおり）、有効期限は任意。
  トークンでトークンの発行・失効はできません（Cookieセッションのみ）。最終使用日時を1分単位で記録します。
- **SCIM 2.0**：`/scim/v2`。`SCIM_TOKEN` によるBearer認証。ユーザーは `userName`=OIDCの`sub`、グループは表示名で、OIDCログイン側と突き合わせます。
  ユーザー削除は無効化（作成者などの参照を保つため行は残す）、グループ削除はそのグループを指すACLも削除します。
  SCIM有効時は、ログイン時の `groups` クレームでグループ所属を上書きしません（SCIMを正とする）。
- **REST API**：JSON。本文は `GET /content` で読み、`POST /content`（Markdown）で書き換えます。書き換えだけは、サーバーがYjsの状態（スナップショットと更新ログ）を読んで、変えるブロックだけのupdateを作り、`Collab.injectUpdate` で保存・配信します。
  OpenAPI定義は `scripts/gen-openapi.py` で作ります。

## 9. 冗長構成・デプロイ

- 各ノードに、`skiwi-app`、Patroni + PostgreSQL、etcd を置く構成です。添付は冗長化した S3 互換ストレージ（各ノードに分散して置くか、外部のもの）に保存します。構築・運用手順は [operations.md](operations.md)。
- **Kubernetesは使わず、systemdまたはDocker Composeを基本にします。** 小規模運用に合わせた判断です。
- 入口は keepalived（VIP）と HAProxy です。
- 無停止デプロイは、1ノードずつドレインして更新します。WebSocketは再接続で復旧します。
- 小規模運用で RPO／RTO の要求が緩い想定のため、Patroniは非同期レプリケーションを基本とします。

## 10. sbtモジュール構成

```
skiwi
├─ core        ドメイン、ACL判定
├─ db          doobie、マイグレーション（Flyway）
├─ collab      WSリレー、updateログ、担当ノード決定・転送、ノード間配信
├─ auth        OIDC、SCIM、APIトークン
├─ storage     S3 互換ストレージのクライアント
├─ notify      メールアウトボックスの送信ワーカー（sbtプロジェクト名は notifier）
├─ api         http4sルート（認証、ページ、検索、添付）
├─ app         起動、設定
├─ shared      バックエンドと画面(Scala.js)で共有するAPIの型
└─ web         Scalactive(Scala.js)で書いた画面
frontend/      Vite の入口。JS のまま残す部分（TypeScript）を window.skiwiLoad で Scala.js の画面へ渡す
               エディタは Tiptap（素の DOM のノードビュー） + Yjs + y-websocket互換プロバイダ
               ビルド成果物は skiwi-app が静的配信、または HAProxy 配信
```

## 11. 既知の課題

- クライアント依存のコンパクション。更新や状態断片が溜まり続けないか、長期稼働で確認します。
- 実機（VM）での構築と障害試験はまだ行っていません（Docker上の試験のみ）。
- 添付やスナップショットの容量増加。保持期間と削除ポリシーを決める必要があります。
- フロントのバンドルサイズ（Mermaidが大きい）。Mermaidは動的読み込みにしているが、初期チャンクの分割は課題です。
